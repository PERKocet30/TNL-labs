# Wire the return path before adding features

TNL Labs should copy Shopify's payments discipline before any of its merchant features, because TNL's market can already take money correctly but cannot hear about money going back. Shopify's published rules for its payment service are short: every money-moving request carries an idempotency key, every outbound call has a tight timeout, webhooks are treated as duplicated, unordered and lossy, and a reconciliation job checks every record against the processor anyway ([Shopify Engineering: 10 tips](https://shopify.engineering/building-resilient-payment-systems); [shopify.dev: webhook best practices](https://shopify.dev/docs/apps/build/webhooks/best-practices)). TNL has two of these already: `settlePaidOrder()` is a status-guarded settle, and one function serves both the checkout redirect and a lazy reconciler, which is the "call it from both places" pattern Stripe recommends. It lacks the rest. `src/pay.js` calls Stripe with raw `fetch`, no `Idempotency-Key` and no timeout. There is no Stripe webhook. `orders` has no record of the fee charged and no `refunded` or `disputed` state. Stock is not held during checkout, so an oversold order tells the seller to refund from their Stripe dashboard, and TNL never learns that the refund happened. `sale_made` and `delivery_confirmed` rep stay awarded either way, which breaks the product rule that rep reflects what other people actually did. Every fix in this list runs on Node built-ins and the Stripe account TNL already has. On features, Shopify's own native set is small: three discount types, self-serve returns from the order status page, and Plus-only bot protection. Everything fancier is pushed to apps, so TNL can match the useful core with a handful of small native builds. Pods, Packwerk, Sorbet-scale tooling, load generators and merge queues answer problems that come with 489 million requests a minute, which TNL does not have.

## Shopify's money rules fit in four sentences, and TNL already follows two

Shopify's canonical description of its Payment Service comes from 2019 and is still the reference. Every mutation requires an idempotency key as an input field. Each request is stored as a row unique on (client, key), and a lock on that pair turns a concurrent duplicate into an HTTP 409 "retry shortly." Each mutation is split into ordered **recovery points**, so a retry resumes at the first step that did not finish ([Shopify Engineering: idempotency](https://shopify.engineering/building-resilient-graphql-apis-using-idempotency)). Shopify is open about the cost: an extra database write on every call, a style new developers find unfamiliar, recovery points that must stay compatible with requests already in flight, and tests for every step and recovery path. It also says true idempotency is "very hard" against a provider that is not itself idempotent. The 2022 follow-up adds the operational rules. Start around **1 second to connect and 5 seconds to read**, because Ruby's 60-second default lets one slow partner tie up the fleet. Key circuit breakers by host, and by merchant country for card traffic, so one region's processor outage doesn't trip the rest. Reconcile both per record (charges, refunds) and in aggregate (balances), logging typed anomalies and auto-fixing them first. Keep business *failures* such as declines separate from *errors* such as partner 500s, and carry a correlation ID from the request into jobs and SQL comments ([Shopify Engineering: 10 tips](https://shopify.engineering/building-resilient-payment-systems)).

Stripe's documentation says the same things in terms of TNL's actual integration. A POST that carries an `Idempotency-Key` has its first result stored and replayed, *including 500s*. Keys can be pruned after 24 hours, and reusing a key with different parameters is an error ([Stripe API: idempotent requests](https://docs.stripe.com/api/idempotent_requests)). For hosted Checkout, Stripe says plainly that **"webhooks are required for fulfillment"** because buyers may never come back to the landing page. Its fulfillment function has to cope with being called "multiple times, possibly concurrently," and should re-retrieve the session and check `payment_status` each time. Stripe recommends calling it from the landing page as well, for speed ([Stripe: fulfill orders](https://docs.stripe.com/checkout/fulfillment.md?payment-ui=stripe-hosted)). Shopify gives app developers the same advice about its own webhooks: verify the HMAC, deduplicate on the webhook ID, don't assume ordering, and "shouldn't rely on" webhooks alone, so run a reconciliation job over everything changed since the last run ([shopify.dev](https://shopify.dev/docs/apps/build/webhooks/best-practices)).

Measured against that, TNL is closer than "no webhook" makes it sound. `/api/market/checkout/done` and `reconcileOrders()` both run `verifySession` → `sessionFits` → `settlePaidOrder`. `sessionFits` binds the paid session to the lead order's `metadata.order_id` and to the exact group total (`src/server-07-cart.js:14-19`). `settlePaidOrder` acts only on `pending` (`src/server-07-orders-sharing.js:98-121`). Because `node:sqlite` is synchronous and no `await` sits between the read and the `UPDATE`, the guard works as a compare-and-set today. Five gaps remain. First, the reconciler only runs when the buyer or seller loads `/api/orders` (lines 134-155), so an abandoned redirect leaves an order `pending` until someone opens the app. Second, there is no idempotency key, which is harmless now because a retry just creates a second unpaid session, but essential the moment TNL sends refunds. Third, there is no timeout, so a hung Stripe call holds the checkout request open. Fourth, there is no stored fee. Commission depends on the seller's rep *at checkout time* (`FEE_BY_LEVEL = {1:10, 2:8, 3:6, 4:4, 5:2}`, `src/db.js:782-785`), so once a seller levels up, TNL can no longer say what it charged on an old order without asking Stripe. Fifth, refunds and disputes are invisible: they happen in the seller's Stripe dashboard and never reach `orders` or `rep_events`.

Two smaller defects in `POST /api/orders/:id/received` (`src/server-07-orders-sharing.js:186-196`) belong with the state-machine fix. The route awards `delivery_confirmed` on a single buyer tap, including on an order that is `paid` but was never marked `shipped`. It then writes `status='complete'` unconditionally, after a read, rather than with `WHERE status IN (...)`. The Depop report already proposes holding delivery rep until the claim window closes cleanly. The Shopify-specific point is narrower: every order transition should be one conditional `UPDATE … WHERE id=? AND status=?` that checks `changes === 1`, so the guard still holds if an `await` later lands between the read and the write.

## Shopify's merchant toolkit is smaller than its marketing

Shopify's built-in discounts are three types: amount off (a product, a collection or the whole order), Buy X get Y, and free shipping. Tiered and stacked discounts need apps ([Shopify Help: discount types](https://help.shopify.com/en/manual/discounts/discount-types)). Self-serve returns are requested from the **order status page**. Merchant rules set eligibility, the return window and who pays return shipping. The merchant approves or declines, and unshipped cancellations go through the ordinary refund flow ([Shopify Help: self-serve returns](https://help.shopify.com/en/manual/fulfillment/managing-orders/returns/self-serve-returns)). Abandoned-checkout recovery starts only once a buyer has entered an email and stayed incomplete for 10 minutes. It is suppressed if the buyer completed the purchase, payment errored, the items are gone, or the payment was blocked as high risk ([Shopify Help: abandoned checkouts](https://help.shopify.com/en/manual/orders/abandoned-checkouts)). Pre-orders and back-in-stock alerts are not native features. Shopify provides Flow triggers for "out of stock" and "back in stock", and apps sell the rest ([PreProduct](https://preproduct.io/docs/pre-order-shopify-flow-actions-and-triggers.md)). TNL already has the pieces for each of these. Price-drop notifications go to people who saved a listing (`server-06-market-stock.js:75`). A quantity edit is how a seller restocks (`server-06-settings-payouts-market.js:298`). The bag already combines shipping per seller.

Drop tooling is thinner still. Shopify's native protection is **Plus-only bot protection**: one scheduled event of at most 60 minutes with a reCAPTCHA or hCaptcha checkpoint, described as "not meant to combat bot-related fraud." Waiting rooms and cart holds come from third parties such as CrowdHandler and Cart Reserve ([Shopify Help: bot protection](https://help.shopify.com/en/manual/checkout-settings/bot-protection); [CrowdHandler](https://www.crowdhandler.com/docs/80001187610-complete-guide-planning-and-executing-a-flash-sale-on-shopify-using-crowdhandler)). Shopify gates an anonymous storefront. TNL's members-only app already has stronger gates: login, the `verified` middleware on checkout, and per-user rate limits. The Complex report's reservation table and drop gates cover the rest, and this report doesn't respecify them.

Shopify Protect matters less for what it covers than for its **condition**. It is free, but only for US stores, Shop Pay through Shopify Payments, and fraud chargebacks. It requires fulfillment with a tracking number from an approved carrier **within 7 days** ([Shopify Protect](https://www.shopify.com/protect)). Collabs has the same shape. Affiliate commission sits in a holding period (30 days by default, configurable from 1 to 90) during which a refund or cancellation voids it ([Shopify Help: pay creators](https://help.shopify.com/cs/manual/promoting-marketing/collabs/merchants/payments)). Both programs pay out only after the facts are settled. TNL does the opposite: it pays rep the instant a session settles and the instant a buyer taps "received," and never claws either back.

On the buyer side, treat Shopify's checkout numbers as marketing. The "up to 36%" checkout lift and "as much as 50%" Shop Pay lift come from an unnamed consultancy with no published method ([Shopify Enterprise](https://www.shopify.com/enterprise/blog/shopify-checkout)). The only named-merchant figure found is Princess Polly at about 1-4%, and Baymard puts wallet-button lift at roughly 8-19% ([CleanCommit](https://cleancommit.io/blog/shop-pay-conversion-rate/)). Baymard's independent abandonment survey is more useful. It finds **extra costs too high in 40%** of US checkout abandonments, total cost not shown up front in 12%, distrust with card details in 19%, and an unsatisfactory returns policy in 13% ([Baymard](https://baymard.com/lists/cart-abandonment-rate)). All four point to the same small builds: show the all-in price early, show a returns and protection line in the bag, and give every order a status page.

## Shopify's architecture endorses TNL's shape, not its tooling

Shopify still runs one very large Rails monolith, with "millions of lines" sorted into "a couple dozen" components. Its own Packwerk retrospective calls the boundary checker "a sharp knife." Packwerk can't see dynamic constants, routes or initializers, so a package with zero violations can still fail at runtime. The authors recommend measuring whether code *runs in isolation*, not counting violations ([Shopify Engineering: Packwerk retrospective](https://shopify.engineering/a-packwerk-retrospective)). TNL's numbered parts are a file-level version of the same idea, and the useful lesson is that one runtime test beats a naming convention. For example, a test can assert that only `pay.js` and `server-07-*` call `createCheckout` and `verifySession`, and that only `db.js` writes `rep_events`. Sorbet's per-file strictness sigils, which reached 80% of files at `typed: true` or stricter with CI failing on type errors ([Shopify Engineering](https://shopify.engineering/the-state-of-ruby-static-typing-at-shopify)), map onto `// @ts-check` with JSDoc in plain JS. Starting with `pay.js` and the order parts would catch the money-path typos that matter most. It needs `typescript` as a dev dependency or an `npx` run in CI, so it needs the owner's approval.

On deploys, Shopify historically ran about 400 commits a day through a merge queue, with "no staging or canary deploys," relying instead on feature flags and fast rollback ([Shopify Engineering: tech stack](https://shopify.engineering/e-commerce-at-scale-inside-shopifys-tech-stack)). TNL's PR → green CI → Railway deploy is the same bet at a smaller size. What TNL lacks is a kill switch for its money paths: an admin "payments paused" toggle, built on the pattern the Studio switch already uses, so a Stripe problem can be contained without a deploy. Shopify's weekly-ratcheting "shitlist" (a checked-in list of existing violations that may only shrink, [RubyEvents](https://www.rubyevents.org/talks/shitlist-driven-development-and-other-tricks-for-working-on-large-codebases)) suits TNL's existing 24KB and palette checks. Its hard extension budgets (64KB UI extensions, an 11-million-instruction Functions cap, [shopify.dev](https://shopify.dev/docs/apps/build/functions/optimize-instruction-counts)) support adding a gzipped size budget on `public/index.html` to `npm test`.

The business model points the same way. In FY2025, merchant solutions, mostly payment fees, were about 76% of $11.56B revenue. Payments penetration was 65.6% of $378.4B GMV, and about 68% by Q2 2026 ([Shopify FY2025 10-K](https://www.sec.gov/Archives/edgar/data/1594805/000159480526000007/shop-20251231.htm); [Shopify Q2 2026](https://www.shopify.com/news/shopify-q2-2026-financial-results)). That works out to merchant-solutions revenue of about **2.3% of GMV**. This is calculated here, not a figure Shopify reports, but it is roughly TNL's level-5 rate. TNL's 10%→2% ladder already ties revenue to seller success. The warning comes from Shopify's June 2025 App Store change, which moved the 0% developer revenue share from the first $1M each year to the first **$1M lifetime**. Developers above that lose about $150k a year, and the change drew press backlash ([shopify.dev changelog](https://shopify.dev/changelog/update-to-shopifys-app-developer-revenue-share); [Business Insider](https://www.businessinsider.nl/shopify-rolled-back-a-lifeline-it-extended-to-app-developers-during-the-pandemic)). A generous rate is easy to grant and expensive to take back. TNL should record `fee_pct` on every order now, so any future change to `FEE_BY_LEVEL` can be grandfathered and audited.

## What to build, in order

Effort: S ≤ 2 days, M 2-5 days, L > 5 days. **SR** = touches payments, auth, uploads or admin and needs `/security-review`. File sizes are tight: `server-07-orders-sharing.js` is 20.0KB, `server-06-settings-payouts-market.js` 21.8KB and `app-17-market.js` 22.4KB. New money code therefore goes in new parts, such as `server-07-webhook.js` and `server-07-refunds.js`. Function declarations are hoisted in the joined runtime, so a later part can define what an earlier route calls. Items already specified elsewhere are cross-referenced, not respecified.

## What only Shopify's scale justifies

Pods and online shard rebalancing exist because a single shared Redis once took the whole company down, and because one flash sale can produce 40,000 simultaneous checkouts ([Shopify Enterprise](https://www.shopify.com/enterprise/blog/shopify-checkout)). One SQLite file has no neighbour to protect. Packwerk exists to coordinate thousands of engineers across millions of lines, and by its authors' own account it is still paying down debt years in. The merge queue solves merge races that one or two committers don't create. Genghis-class production load generation across three GCP regions, region-evacuation drills, a Resiliency Matrix and an incident bot with three roles are the price of 81 million BFCM shoppers. Semian bulkheads keyed by country, a custom JIT, Wasm-sandboxed Functions with instruction budgets and Hydrogen headless storefronts all answer problems of third-party code and multi-storefront hosting that TNL does not have. Within payments, Shopify's full recovery-point framework is also scale-only. TNL has one remote side effect (create a session) and one local transaction (settle), so an idempotency key plus a status guard covers it. A refund adds one more remote step, which still doesn't justify a framework. The networked buyer products (Shop Pay's pre-opted identity, Shop Campaigns' pay-per-acquisition, agentic syndication into ChatGPT and Gemini) depend on a buyer network of 100 million or more. TNL's version of that network is its own feed and "Shop this post."

Some uncertainty remains. Shopify has not published its internal payment state machine or how it reconciles against Stripe in particular. The Stripe Connect webhook details for Standard direct charges (a Connect endpoint whose events carry an `account` field) come from general Stripe knowledge and should be confirmed at docs.stripe.com/connect/webhooks before #4 is built. Commission handling on refunds (`refund_application_fee`) is a policy choice, not a technical one. No data on TNL's checkout volume was available, so the order of this list reflects risk, not observed incidents.

## Conclusion

The pattern across Shopify's money systems is not scale but **settlement before reward**. Collabs holds commission until the refund window closes, Protect pays only once tracking exists, and webhooks are always backed by a reconciler that assumes some were lost. TNL has built the reward half carefully: an append-only `rep_events` log, server-only rep, and a fee ladder tied to that rep. But it attaches rewards to the *first* sign of a sale and has no path for that sign to be reversed. Closing that loop is mostly plumbing that uses only Node built-ins: a timeout, an idempotency key, a fee column, a signed endpoint, a conditional state transition and a sweep.

One second-order effect makes this urgent rather than tidy. Because commission falls as rep rises, unreversed `sale_made` rep from refunded or oversold orders lowers TNL's own take on that seller's future sales. A seller could farm levels with self-refunded purchases by alts. The money bug is also a rep-integrity bug and a revenue bug. That is why P0 should ship as one reviewed change, before discounts, drops or affiliate payouts put more money and more incentive through the same path.
