# TNL ships like 2016 Instagram, checks like 2010

*Research synthesis, 8 October 2026. Sources: the four notes in `research_notes/TNL Labs code vs Instagram code/` (a read-only audit of this repo at HEAD 7b6412c, plus Instagram server, client and engineering-process research) and the earlier `research_notes/Instagram features and backend/` notes. Repo facts link to files in this repo. **Evidence caveat:** instagram-engineering.com (Medium) returned HTTP 503 and the Medium mirrors returned 403 throughout this research. Every claim attributed to an Instagram Engineering post below comes from search-result excerpts of that post, or from coverage of it (InfoQ, O'Reilly, Meta's own blogs), not from a full read. Claims that rest on a single secondary source are flagged where they appear.*

TNL Labs' code is Instagram's 2011 architecture run with a 2016 delivery pipeline, and it is missing the layer Instagram added in between: machine-checked code. Both apps are single monoliths where every route loads into one process. Instagram never left that shape: by 2019 its "few thousand Django endpoints" were still "loaded up and served together" ([Instagram Engineering](https://instagram-engineering.com/8f498ab71a0c)). TNL is the same idea about four orders of magnitude smaller: about 8.2k server lines against a reported ~20M for Instagram (a secondary figure, [pydevtools](https://pydevtools.com/handbook/reference/pyrefly/)). On delivery TNL is already ahead of where its size would predict: merges deploy automatically, CI gates every PR with about 1,000 assertions plus a real-browser walk at phone and computer width, and a post-deploy probe confirms the new commit is serving. Where it trails even 2016 Instagram is static checking. TNL has no linter, no types and no security analysis, and that gap is sharpened by a design choice Instagram never had: about 535 client declarations and 30 server parts concatenated into one shared scope. The same gap shows up in a few concrete security risks. A bearer token sits in `localStorage` and the UI renders through 44 `innerHTML` sites guarded by hand-written `esc()` calls, with no Content-Security-Policy. Sessions never expire, CORS accepts every origin, and payment state is confirmed by polling instead of signed webhooks. Almost everything worth adopting next needs **no new dependency**: security headers and a CSP hash computed by the existing assembler, session expiry, a Stripe webhook verified with `node:crypto`, source-to-sink security tests in TNL's existing regex-test style, a schema version, a request-timing table with deploy markers, and Railway platform settings for health-gated deploys and rollback. Only off-volume backups require a new service, and only real type-checking or ESLint requires a new (CI-only) dependency. Instagram's compilers, JITs, build systems, GraphQL and experiment platforms solve problems of hundreds of engineers and millions of lines. TNL should copy the **order** in which Instagram added rigor, not the tools it built to do it.

## Same monolith shape, four orders of magnitude apart

The architectural resemblance is closer than the size gap suggests. In 2011 Instagram reached 14 million users with three engineers on stock, proven parts: Django on Gunicorn, PostgreSQL, Redis, memcached, Gearman for async work, and S3/CloudFront for photos ([Instagram Engineering, 2011](https://instagram-engineering.com/what-powers-instagram-hundreds-of-instances-dozens-of-technologies-adf2e22da2ad); [High Scalability](https://highscalability.com/instagram-architecture-14-million-users-terabytes-of-photos/)). TNL is even barer. It runs one Express 4 process and one SQLite file through Node's built-in `node:sqlite`, has exactly **four runtime dependencies** (`express`, `cors`, `bcryptjs`, `ffmpeg-static`), and has no devDependencies at all ([package.json](../package.json)). It calls Stripe and Resend with raw `fetch` rather than SDKs ([src/pay.js](../src/pay.js); [src/mail.js](../src/mail.js)), and pushes realtime over Server-Sent Events from an in-process `Map` ([src/server-10-live.js](../src/server-10-live.js)). In Instagram's terms it is pre-2011: there is no cache tier, no queue and no second box, and nothing yet forces one.

Instagram's server language and framework never changed. Python and Django ran from 2010 to 2026. The Python 2→3 move in 2017 happened inside the main branch, with the code kept runnable on both versions while features kept shipping ([PyCon 2017 recap](https://www.blog.pythonlibrary.org/2017/05/21/python-2017-second-day/); [Caktus Group](https://caktusgroup.com/blog/2017/06/12/python-instagram)). Everything since has been rigor added *around* the monolith: linting, types, codemods, taint analysis, and eventually a forked runtime. The monolith itself was never the problem. Instagram's pain came from scale *inside* it. Circular imports were "the biggest obstacle to refactoring" and caused several outages, startup imported about 28,000 modules, and a developer reload averaged about 50 seconds ([Meta, Lazy Imports, 2022](https://developers.facebook.com/blog/post/2022/06/15/python-lazy-imports-with-cinder)). TNL avoids imports entirely. `src/assemble.mjs` sorts the numbered `server-NN-*.js` and `app-NN-*` parts and `.join("")`s them into `src/server.runtime.js` (~393KB) and `public/index.html` (~601KB) on every boot ([src/assemble.mjs](../src/assemble.mjs)). The side effect is TNL's version of Instagram's import-order problem: **file boundaries are not module boundaries**. Every part shares one scope, so load order and name collisions are the risk, and only tests stand guard over them.

## A 2011 architecture with 2016 delivery and pre-2016 guardrails

Each part of TNL maps to a different year of Instagram's history. **Architecture is 2011**: one framework app, few moving parts, stock components, "do the simple thing." **Delivery is 2016.** Instagram's continuous deployment then meant every commit tested by Jenkins, then a canary, then the fleet or a rollback, with authors told by chat and deploys overlaid on graphs ([InfoQ](https://www.infoq.com/news/2016/04/continuous-deployment-instagram); [Instagram Engineering](https://instagram-engineering.com/continuous-deployment-at-instagram-1e18548f01d1)). TNL has the same skeleton at small scale. PR CI runs `npm test` and the Playwright walk ([.github/workflows/tests.yml](../.github/workflows/tests.yml)). A merge deploys. `after-deploy.yml` polls `/api/health` until it reports the merged SHA, then runs the scientist's read-only checks ([.github/workflows/after-deploy.yml](../.github/workflows/after-deploy.yml)). A second Railway service reruns those 8 checks daily at 18:45 UTC; this is documented in [README.md](../README.md) and [RAILWAY.md](../RAILWAY.md) but is not visible in the workflows, so it was not verified from the repo. Cadence is comparable in count, though not in kind. TNL logged 47 commits on 2026-09-29 alone, against Instagram's 30–50 deploys a day in 2016, but TNL deploys per merged PR, not per commit, so its "suspect pool" for a bad deploy is a whole PR.

**Static checking is pre-2016.** Instagram adopted Flake8 in 2016 ([Meta, Fixit 2](https://engineering.fb.com/2023/08/07/developer-tools/fixit-2-linter-meta/)), runtime-traced types and a checker in 2017, autofix codemods around 2019, and taint analysis on diffs in 2020 ([Pysa](https://engineering.fb.com/security/pysa/)). Each layer arrived when the codebase or team outgrew what review alone could catch. TNL has none of them. Its substitute is unusually strong prose: about **14% of server lines and 17% of client lines are comments**, many versioned and dated ("PALETTE v1.0 — 2026-09-29") and explaining why a choice was made ([src/palette.js](../src/palette.js); [src/db.js](../src/db.js)). That suits an AI-assisted solo team, but no machine checks it. The audit's sharpest example is `boot.test.mjs`. It exists because a function was missing from the login path and nothing caught it before production; the test now runs the whole client script in a `node:vm` sandbox with a stub DOM ([test/boot.test.mjs](../test/boot.test.mjs)). In the concatenated client script, a second top-level `function` with an existing name silently replaces the first. A linter or type checker catches that in milliseconds. TNL currently relies on a test someone remembered to write.

**Observability is roughly 2011 plus Sentry, and reliability is ahead of 2011 but behind 2016.** TNL has crash reporting and a deploy-landed check, and it has a behaviour signal Instagram documented only at device-lab scale: the in-app glitch watcher, which reports rage taps, layout jumps, slow screens and failed actions without sending content ([src/app-19-glitch.js](../src/app-19-glitch.js)). It has no request-latency history, no deploy markers on any chart, no tested restore, and no written rollback path.

**Testing is the one area where TNL is denser than its stage.** About 275KB of tests guard about 1.1MB of source. That is the right investment, because Instagram's own CD effort first stalled on "a flaky, slow test suite" ([InfoQ](https://www.infoq.com/news/2016/04/continuous-deployment-instagram); [O'Reilly](https://www.oreilly.com/content/instagrams-5-principles-for-implementing-and-scaling-continuous-deployment/)). The weakness is what the assertions check. A meaningful share regex the source text rather than exercising behaviour (the mail, cart, profile-card and cloudflare suites read source files 10–17 times each). Such tests pass when behaviour breaks but the text still matches, and they fail on harmless refactors. Regex tests are TNL's equivalent of Fixit's local lint rules and belong on invariants. Logic should be tested by calling it.

## Client and data layers carry TNL's real structural debt

On the client, Instagram's best-documented web wins need no framework. The 2019 "Making instagram.com faster" series reports about **50% cumulative improvement in feed page load**. It got there by preloading data queries, flushing the HTML early with data pushed alongside it (+14% display completion on desktop, +23% on mobile), painting a cached feed from IndexedDB before revalidating, and not executing code until it is used ([Part 2](https://instagram-engineering.com/making-instagram-com-faster-part-2-f350c8fba0d4); [Part 3](https://instagram-engineering.com/making-instagram-com-faster-part-3-cache-first-6f3f130b9669); [Part 4](https://instagram-engineering.com/making-instagram-com-faster-code-size-and-execution-optimizations-part-4-57668be796a8); all via excerpts). TNL serves one HTML document from its own server, so it can inline the first page of feed JSON into the response and paint the last-seen feed from its existing service worker cache. The structural lesson comes from iOS. IGListKit treats a list as a pure function of an array of models and diffs old against new by identity, so only changed cells move ([GitHub IGListKit](https://github.com/Instagram/IGListKit)). TNL's `render()` rebuilds every scroller on every state change ([src/app-09-render-nav.js](../src/app-09-render-nav.js)). That is why it needed a whole motion and scroll-restore layer and a glitch watcher to hide the jumps. Keying list items by `data-id` and patching only changed nodes removes the cause rather than masking it.

TNL is already ahead of most small apps, and in step with Instagram, on theming. Instagram's 2019 iOS dark mode was built on "a semantic color palette that our design systems team created" behind a deliberately tiny API, because "it's harder to misunderstand or misuse APIs if there are fewer of them" ([Instagram Engineering, Dark Mode](https://instagram-engineering.com/instagram-darkmode-58802b43c0f2)). `src/palette.js` plus a drift test is the same design ([src/palette.js](../src/palette.js)). Atomic CSS and StyleX solved a homepage that loaded 400KB+ of CSS of which about 90% went unused, written by thousands of engineers ([Meta, 2020](https://engineering.fb.com/2020/05/08/web/facebook-redesign/)). TNL's 13 CSS parts do not have that problem.

The data layer is sound for one box but has three code-level gaps:

- **No schema version.** Migrations are 37 `if (!cols.includes(...)) ALTER TABLE ADD COLUMN` guards, with no version table and no down path ([src/db.js](../src/db.js)). Instagram's 2016 practice was staged schema change behind toggles: dual-write, change the DB, backfill, switch reads, keep old writes as a fallback ([InfoQ](https://www.infoq.com/news/2016/04/continuous-deployment-instagram)). That matters for TNL because a Railway rollback restores the old code image but never the old schema ([Railway docs](https://docs.railway.com/guides/roll-back-bad-deploy)). Every migration must stay additive so the previous build can still run.
- **Weak transaction coverage.** `awardRep()` inserts the ledger row and updates `users.rep` without a transaction, and only four explicit `BEGIN`/`COMMIT` blocks exist in the whole server.
- **Everything is synchronous.** `DatabaseSync` and the per-response `zlib.gzipSync` both block the event loop.

SQLite's own guidance calls under 100K hits a day conservative, with 10× demonstrated ([sqlite.org](https://www.sqlite.org/whentouse.html)), so the engine is not the bottleneck. The earlier backend report already prescribes the operational fixes and they are not repeated here: `busy_timeout`, backups moved off the main thread, a SQLite `jobs` table, FTS5, SSE replay, and the rep-ledger integrity work.

## Five security gaps that hand-written discipline does not close

TNL's security basics are deliberate and well commented:

- bcrypt password hashes and random 48-hex bearer tokens;
- an admin check enforced on the server for every admin route, plus an audit log of admin writes;
- 43 rate-limited routes;
- uploads sniffed by their first bytes, so a file lying about its type is rejected after one chunk;
- an SSRF guard on the link unfurler that refuses any private DNS answer and re-checks every redirect;
- `Cache-Control: no-store` on every API response;
- Stripe direct charges with no card data stored.

([src/server-01-boot.js](../src/server-01-boot.js); [src/server-10-links.js](../src/server-10-links.js); [src/pay.js](../src/pay.js))

The gaps are the kind that Instagram's tooling exists to catch automatically. Pysa defines sources (request input) and sinks (SQL, `eval`, HTML output), traces data between them on every proposed diff, and returns results in about an hour. Of 330 unique issues it flagged on diffs, 49 (15%) were significant and 131 (40%) were real but already mitigated ([Meta, Pysa](https://engineering.fb.com/security/pysa/)). Facebook's Zoncolan found 43.3% of severe security bugs, more than manual review or the bug bounty ([CACM 2019](https://cacm.acm.org/magazines/2019/8/238344-scaling-static-analyses-at-facebook/pdf)). TNL has no such check, so five gaps stand.

**XSS becomes account takeover.** Rendering goes through 44 `innerHTML` assignments protected by 411 manual `esc()` calls ([src/app-07-theme-labs-api.js](../src/app-07-theme-labs-api.js)). The session token lives in `localStorage("tnl-token")`, and no Content-Security-Policy, `X-Frame-Options`, HSTS or `X-Content-Type-Options` header is set. One missed `esc()` on a user-controlled field therefore hands any visitor's token to the attacker, with nothing to contain it.

**Sessions never expire.** The `sessions` table has no expiry column, so a stolen token works until logout, a password reset or an admin action ([src/db.js](../src/db.js)).

**Passwords and CORS are permissive.** The minimum password is 6 characters, and `app.use(cors())` accepts every origin.

**Payments rely on polling.** There is no Stripe webhook handler. A checkout is confirmed by a client-triggered `verifySession` poll, and refunds and disputes are never seen ([src/pay.js](../src/pay.js)). The earlier research showed this is also a rep-integrity hole: rep earned from a sale survives the refund.

**Rate limits reset on every deploy.** The rate limiter lives in process memory and clears on each restart ([src/server-01-boot.js](../src/server-01-boot.js)). That is acceptable for one instance, but worth knowing.

The architecture fixes the first gap more cheaply than usual. `assemble.mjs` already produces the single inline `<script>` at boot, so it can also compute that script's SHA-256 and the server can send `Content-Security-Policy: script-src 'self' 'sha256-…'`. That gives a strict CSP with no nonce plumbing and no dependency. Moving the token to an `HttpOnly; Secure; SameSite=Lax` cookie would close the gap more fully. That is a larger change: the bearer-token API would need CSRF protection, and the SSE ticket flow would need rework. It should follow the CSP, not precede it.

## What Instagram's scale justifies, and what TNL should take now

Most of Instagram's tooling exists to coordinate hundreds of engineers and millions of files, and TNL should skip it:

- **Runtime work.** Cinder's JIT and Static Python, GC freezing for copy-on-write workers ([Instagram Engineering, GC](https://instagram-engineering.com/dismissing-python-garbage-collection-at-instagram-4dca40b29172)), and lazy imports answered 28,000-module startups. TNL has no module graph at all.
- **Build systems.** Buck frameworks, remote caches and Kosabi answered link times over "millions of source files" and an 8M-line Kotlin codebase ([@Scale iOS](https://atscaleconference.com/improving-instagram-ios-build-speeds/); [@Scale Kotlin](https://atscaleconference.com/kotlin-instagram/)).
- **Client data and style frameworks.** Relay/GraphQL per-component data declarations, and atomic CSS, answer many-team coordination problems.
- **Testing and performance infrastructure.** Predictive test selection, MobileLab and CT-Scan device labs, ServiceLab and FBDetect, and LLM test generation at fleet scale ([Meta, FBDetect](https://tangchq74.github.io/FBDetect-SOSP24.pdf); [TestGen-LLM](https://arxiv.org/pdf/2402.09171)) all assume a suite too big to run whole, or a fleet big enough to make a 0.005% regression visible.
- **Experimentation and rollout.** A/B experimentation platforms and percentage canaries across thousands of hosts need traffic TNL does not have. Its own 7/30/90-day admin numbers support before-and-after comparisons, not statistically powered experiments.
- **Sharding and paid bug bounties.** Neither is needed. Meta paid over $4M in bounties in 2025 alone ([SecurityWeek](https://www.securityweek.com/meta-paid-out-4-million-via-bug-bounty-program-in-2025/)); a `security.txt` contact address gets most of the benefit at TNL's size.

The ideas behind those tools do scale down, and most of them map onto mechanisms TNL already has:

- **Pysa becomes a grep.** A source-to-sink check fits as a `test/security.test.mjs` in TNL's existing regex style: every `/api/admin` route chains `admin`, no `prepare()` or `exec()` interpolates `req.*` into a template literal, and every `innerHTML` interpolation passes through `esc()`. The 2021 outage carries a related warning: Meta's audit tool, the check that should have blocked the bad command, itself had a bug ([Meta, 2021](https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/)). TNL's safety checks therefore need tests of their own, for example asserting that a non-admin is actually refused.
- **Gatekeeper becomes the Settings table.** Instagram separates shipping code from launching a feature, so the usual fix for a bad feature is flipping a flag, not reverting ([Meta, 2017](https://engineering.fb.com/2017/08/31/web/rapid-release-at-massive-scale/)). The Settings table can do the same if every risky feature ships behind a switch with an "admins only" state before "everyone", which mimics Meta's employees → 2% → 100% tiers.
- **Sauron becomes a `deploys` table.** Rows written at boot can be drawn as markers on the admin chart, and Sentry's `release` set to the commit SHA.
- **Scuba becomes a trimmed `req_metrics` table** holding route, status and milliseconds. It feeds p50/p95 and 5xx charts, and the scientist can fail when its timings exceed twice the trailing average.
- **Meta's probabilistic flakiness score** ([Meta, 2020](https://engineering.fb.com/2020/12/10/developer-tools/probabilistic-flakiness/)) becomes "retry an e2e step once and log flaky versus failed."
- **ACH's mutation-guided testing** ([arXiv 2501.12862](https://arxiv.org/pdf/2501.12862)) becomes a script, or an AI-agent prompt, that plants a plausible bug in `FEE_BY_LEVEL`, `REP`, payout maths or `tickEvent()` and confirms a test goes red. TestGen-LLM's acceptance rule also transfers to AI-written tests: a new test must build, pass repeatedly and cover something new, or it is deleted.

## Conclusion

The comparison reverses the usual small-team story. TNL is not a toy version of Instagram that needs Instagram's machinery. It is a disciplined monolith whose **process** (small PRs, CI gates, post-deploy probes, kill switches, an audit log, an append-only ledger) is already in the shape Instagram took years to reach. Its risk sits where Instagram's tools sit and TNL has none: the moment a human or an AI agent forgets an `esc()`, a transaction, an admin check or a unique name, nothing mechanical notices. TNL's concatenated parts, one shared scope and AI-generated commits arriving at dozens a day make that missing rung more urgent than raw size would suggest. Most of it is buildable in TNL's own idiom of plain-Node tests and boot-time assembly, without any new dependency.

The most transferable thing about Instagram's history is its order, not its tools. It kept the monolith and added one guardrail at a time, each when the previous layer stopped catching enough: lint, then types, then autofix, then taint analysis on every diff. For TNL that order starts with the security tests and headers, because they are cheap and close a live takeover path. Typed money code is next, and the only step worth asking the owner for a CI-only dependency. The evidence for the Instagram side has limits that should be stated plainly. Most Instagram Engineering posts were read through excerpts, the 20M-line figure, the ">1% of hosts" canary pause and the SEV-review process rest on secondary sources, and instagram.com's current web stack, along with TAO, GraphQL and Configerator usage, was not confirmed from primary sources. None of those gaps changes the recommendations, which rest on TNL's own code.
